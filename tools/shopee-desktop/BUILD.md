# Build on Windows 10

Use Python 3.13, Windows OpenSSH Client, and Microsoft Edge WebView2 Runtime. WebView2 must be present on the machine running the app. The build commands below are for the coordinator's Windows machine; no packages are installed on the application host.

Build from `tools/shopee-desktop` in a repository checkout: the build also bundles `vendor_pychrome/` and the shared file `../opencli-metric/clis/metric/request-in-page.js`. Open PowerShell there:

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
New-Item -ItemType Directory -Force "$env:APPDATA\tdn-shopee-flow"
Copy-Item .\config.example.json "$env:APPDATA\tdn-shopee-flow\config.json"
```

Edit that config. Replace `<user>@<host>` and `<repo>` with the owner's SSH destination and repository folder. These placeholders are intentionally unusable until replaced. Set up SSH authentication and known-host verification beforehand; `BatchMode=yes` prevents a hidden password prompt. The SSH command ends in `bash -s` so the remote POSIX script is read from stdin.

`remoteScript`, `runsRoot`, `presetsRoot` and `remoteEnvFile` accept only paths matching `^(\$HOME/)?[A-Za-z0-9_./-]+$`. Use `$HOME/` for a remote home-relative path, not `~`. Optional paths may be null. `remoteEnvFile` is optional: if present remotely, it is sourced there; the desktop never reads or displays its contents. Keep configuration outside the executable. Do not put credentials in it.

`TDN_SHOPEE_APP_CONFIG` can override the default config location with a full local file path. Config changes take effect on the next bridge call. `timeoutSeconds` defaults to 30 and must be a positive whole number.

Check the connection without opening a window:

```powershell
.\.venv\Scripts\python.exe .\tdn_shopee_app.py --check
```

This prints one JSON line and exits 0 when connected, 1 otherwise. A connected result with `readonly: true` means the guard is active; it is a valid connection. The check reads only the remote guard and runs-root setting.

## Step 1: Metric in the user's own Chrome

The **Tạo lượt mới** screen starts with the step 1 card. It is a port of the coworker app MetricA (`src/browser.js`, `main.js`, renderer card), in `tdn_metric_browser.py`:

1. **Mở Metric** opens the real Chrome (Chrome, then Edge; same five paths and flags as MetricA, 20 s wait, reuse of the app's Chrome when it is already open) with the app's own profile `%APPDATA%\tdn-shopee-flow\metric-chrome-profile` and a debug port on 127.0.0.1 only. The port and that Chrome's browser socket id are kept in `metric-debug-port.txt`; a saved port is reused only while it is still that same Chrome. Chrome opens `about:blank`; the app attaches to that tab, enables network events, then navigates it to `https://metric.vn/analytics`, so the first request is not missed.
2. Every 2 s the app reads Chrome's tab list and attaches only to `page` tabs on `metric.vn` / `www.metric.vn` (vendored pychrome: one connection per tab, so a Google sign-in tab is never attached). A tab whose main frame starts loading another host is detached at once; it is attached again once it is back on Metric. The app never enables `Runtime`, never closes Chrome and never opens, focuses or closes a tab.
3. For each `POST https://apiv4.metric.vn/v2/market/analytics/products/` the app keeps the newest request body per tab, in memory only (`Network.getRequestPostData` when the event has no body). The card shows only a Chrome open/closed pill (every 3 s); it shows no filter line and has no name box.
4. **Lấy bình luận Shopee** freezes exactly the newest products request seen on any Metric tab (if its body is still being read it waits up to 5 s; if it is still missing or unreadable the click is refused with «Trang Metric chưa gửi xong bộ lọc mới…» / «App chưa đọc được bộ lọc mới nhất…», never an older filter), blocks double clicks, refuses with a yellow warning «Bộ lọc chỉ có k sản phẩm Shopee, cần ít nhất N.» and sends and keeps nothing when the answer has fewer distinct Shopee `product_base_id` values (`1__…`) than the choice needs (N for Top N, 1 for «Tất cả»), names the run from Metric's search box (the first search keyword, trimmed and cut to 120 characters; with no search keyword the app uses `Metric DD/MM–DD/MM/YYYY` from the filter period, or `Metric DD/MM/YYYY–DD/MM/YYYY` when the two dates fall in different years), changes only `limit` = 100, `page` = 0, `sort_by` = `revenue_custom__desc`, and runs the shared `requestV3InPage` (the same file `v3-capture.js` imports) in that tab with `Runtime.evaluate` (`awaitPromise`, `returnByValue`, 60 s). Every click first (before the filter is frozen, so a still-loading or unreadable filter is pictured too) saves one full-page picture of the newest request's Metric tab on this PC only (`Page.getLayoutMetrics` + `Page.captureScreenshot` with `captureBeyondViewport` and a full-page clip; since app 1.2.0 `format='webp'`, `quality=80`, or PNG when one side of the picture is over 16383 px, the WebP limit) as `evidence/metric/metric-<local YYYY-MM-DD-HHMMSS>.webp` (`.png` for the big-page case): on success, on the below-5 warning and on failure (a failure then says the picture was kept; there is no second failure picture). The click makes `evidence/` and `evidence/metric/` without the evidence cleanup, so earlier evidence and pictures stay. No picture when the page size is unknown (never a viewport-only one), when either folder or the file is a link or junction, or when the folder cannot be made. A failed picture never blocks the click, and nothing of it is sent to the server: the `m1-import` payload is unchanged. The answer is sent as `m1-import --stdin` (`metric-user-page-import-v1`, see the shared contract) with one UUID `importId` per click and the form's `productSelection` (CONTRACT-F644): group «Sản phẩm bán chạy», «Top N» (1–100, default 5, «Lọc trùng») sends `{"mode":"top","count":N}`, «Tất cả» («Không lọc trùng») sends `{"mode":"all"}`. An old backend takes a missing field as top 5 and refuses other values with `IMPORT_INPUT_INVALID`; there is no fallback. The last choice sent is kept in `product-selection.json` next to `config.json` (the web view keeps no storage) and the form opens with it. The payload stays in memory until the server confirms it, so **Gửi lại** resends the same payload without asking Metric again; **Bỏ và lấy lại từ Metric** drops it.
5. When `m1-import` returns the run, the click's picture is renamed `<runId>-metric-full-page.webp` (or `.png`; unless that Metric tab sent a newer products request while the picture was taken: the page may then show another filter, so the picture stays an unlinked `metric-<time>.webp` and the run has no local picture) (**Gửi lại** keeps and links the same picture).
   **Kept online 10 days (app 1.2.0).** Right after the run exists the page calls `uploadMetricShot`, which returns at once and sends the linked picture in a background thread (`tdn-metric-shot-upload`, one per run), so «Lấy bình luận Shopee» never waits for it: `metric-shot-upload-url --run <id> --content-type image/webp|image/png --bytes <n> --sha256 <hex>` (`metric-shot-upload-v1`: a 10-minute presigned PUT for the immutable, content-bound key `metric-shots/<runId>/<sha256>.webp|png`; the URL signs `content-type;host;x-amz-content-sha256` with the real body hash, so storage refuses any other bytes and a leaked URL can only ever write that same content), an HTTP PUT of the bytes from Python (`urllib.request`, the signed `Content-Type` and `x-amz-content-sha256` headers, 60 s) **straight to Cloudflare R2, not through the relay**, then `metric-shot-confirm --run <id> --key <key> --sha256 <hex> --bytes <n>`: the key must be this run's key for exactly that hash; the server HEADs the object, checks its size and creates `<run>/m1/metric-shot-r2.json` `{key, sha256, byteSize, contentType, uploadedAt, deleteAfter}` exclusively (hard link of a complete temp file: the first confirm wins; the same key, hash and size again returns the stored record; anything else is `METRIC_SHOT_ALREADY_UPLOADED`, and the loser's object simply expires) (`deleteAfter` = `uploadedAt` + 10 days; answer `metric-shot-r2-v1`). Only then is the local file deleted: after the folder chain is checked for links and junctions the file is moved atomically to a unique hidden name in the same folder, hashed through an open handle, its lstat identity must equal the handle's, the chain is checked again, and only then is the hidden name deleted; any mismatch moves it back. So the delete checks digest and file identity after an atomic rename; a same-user process able to swap the folder during the final instant could still redirect the unlink. This is accepted for a single-user desktop app. Any failure keeps the local file and shows nothing. At most one attempt per run every 60 s on every start path (kept in the bridge; the first attempt after the run is created is always allowed); the next details load after that, `metricShotState` (`metric-shot-view-url`) sees a local picture and starts the upload again. `metricShotState` reads the server first, then takes the retry decision and the `uploading`/`local` snapshot in one step under the upload lock; when an upload finished while the server was asked, it asks the server once more, so its one answer is coherent. **The page never decides from what it read before:** «Xem ảnh Metric» and «Tải ảnh» choose their source at click time in the bridge (local → online with a fresh link → old server picture). For every run that is not an old run with the server's `full-page.png`, both buttons are on whenever there is a picture on this PC or the app is connected; off only when offline without a local picture (note «Ảnh chỉ lưu trên máy đã lấy dữ liệu»). The note is information only: each opening of a run's details does exactly one `metricShotState` read (a late answer for a run no longer open is ignored), and a click that finds nothing sets the note from its own answer. Both clicks also send `oldKnown` (app 1.2.1): true when the page has the run's step results, so a null `sha256` means «no old picture» and the bridge reads no `moduleOutputs`; false while they load or failed (the bridge looks it up as before); a click's «không có ảnh» / «đã tự xóa» answer is shown even while the step results are unknown, until the next opening. After a background upload nothing is pushed to the page: the next click or the next opening is right by construction. `metric-shot-upload-url` answers `METRIC_SHOT_ALREADY_UPLOADED` when the run already has a record; the app then only confirms again (same key, hash and size), so a confirm that worked but a local delete that failed is finished on the next try. With no credential file on the server (`R2_NOT_CONFIGURED`) or an older server (`USAGE`) the app behaves as before: the picture stays on this PC only. The bucket's lifecycle rule (set by the coordinator) deletes objects after 10 days.
   **Xem ảnh Metric** opens the picture **inside the app**: a full-width viewer over the page (scroll down for tall pages, «Đóng» or Esc closes; `<img>` only, no file written, no OS viewer). Source order: the local picture (sent as a data URL), else `metric-shot-view-url --run <id>` (`metric-shot-view-v1`: `AVAILABLE` with a 15-minute presigned GET, `EXPIRED` when the record is there but the object is gone or past `deleteAfter`, `NOT_UPLOADED`), else the server's old `full-page.png` for older runs (unchanged: downloaded and opened as before). Note (no local picture, connected): `AVAILABLE` → «Ảnh lưu đến dd/mm/yyyy» (past `deleteAfter`: «Ảnh Metric đã tự xóa sau 10 ngày.»); `EXPIRED` → «Ảnh Metric đã tự xóa sau 10 ngày.»; `NOT_UPLOADED` → «Lượt này không có ảnh Metric.»; no answer → no note. A view or save click that finds nothing shows the same sentence (save answers `METRIC_SHOT_EXPIRED` / `METRIC_SHOT_NOT_UPLOADED`). **Tải ảnh** next to it chooses its source at click time and saves a copy through the native save dialog from the local picture if it is still there, else the online copy (a fresh view link, exactly `byteSize` bytes), else the old server picture (default `<run name>-<runId>.webp` or `.png` after the real type, in Downloads, unsafe characters replaced; the original stays; cancel does nothing; «Đã lưu ảnh» on success).
   Server side: AWS SigV4 in the standard library (region `auto`, service `s3`, path style `https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com/<R2_BUCKET>/<key>`; query-signed PUT (signed payload hash) and GET (`UNSIGNED-PAYLOAD`), header-signed HEAD/DELETE). Credentials: `~/.config/tdn-shopee/r2-metric-shots.env` (`R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`; path override env `TDN_METRIC_SHOTS_R2_FILE`). The secret is never printed, logged or returned. `--run` is checked like every run command, any key other than `metric-shots/<runId>/<--sha256>.webp|png` is refused, `--bytes` is at most 32 MB and `--content-type` only `image/webp` or `image/png`. The relay allowlist needs the three new subcommand names. After import the app calls `run --run <id> --detach` (the whole flow, `detached-v1` like `m2`). On a user-page run the server runs step 2 → step 3 → step 4 and never step 1; the run is followed in the existing step 3 and step 4 screens. Listening stops once the run exists; **Mở Metric** starts it again.
6. **Xóa lượt** in the run details header asks «Xóa lượt này?» («Xóa cả bình luận. Không khôi phục được.», «Hủy» / «Xóa»), then calls `delete-run --run <id>` (not detached; `run-delete-v1`). On the server the run's online Metric picture is deleted too when the run has a record (signed DELETE, best effort: a failure never blocks the run deletion; the 10-day rule removes it anyway). On success the run's local `<runId>-metric-full-page.webp` (or `.png`) is deleted (never through a link or junction), the app leaves the run, refreshes the list and shows «Đã xóa lượt». `RUN_ACTIVE` shows «Lượt đang chạy. Dừng trước khi xóa.» in the box.

## Create a run and add a product (old runs)

The **Tạo lượt mới** screen is one form: product, date period, collection policy, summary, then create. The primary button is **Tạo lượt** for an existing product and **Lưu sản phẩm và tạo lượt** when the inline new-product option is selected. Creating a run, including saving a new product first, never starts a lookup or review collection; only **Bắt đầu lấy dữ liệu** does. The confirmation states that starting uses one sales-data lookup for the run, then chooses links and collects comments, and gives no ETA.

A new run is sent as `new-run-v1` input with `{presetId, endDate, collectionPolicy}`. On the wire, `collectionPolicy` has exactly four keys: `mode` (`all`, `with-comments`, `stars`), sorted unique `stars` (`1..5`, empty unless mode is `stars`), `totalPerLink` (`1..2000`), and `allocation` (`pooled`, or `equal-stars` only in `stars` mode). The remote stores the full canonical request-v2 policy (`format=shopee-review-policy-v1`, `textRule=comment-or-attributes-v1`, `order=native-filter-ascending-stars-v1`) internally. The bridge rejects a request containing both `collectionPolicy` and the legacy `reviewCapPerLink`, and still accepts the old cap-only shape (`1..300`) for compatibility.

- Required product fields for an inline product: display name (at most 120 characters), primary keyword (at most 200, no comma), category. Optional second keyword (at most 200, no comma). Commas are rejected because query chips split at commas.
- The preset ID is derived from the display name as a lowercase ASCII slug (at most 64 characters) and is not shown in the form. If the slug already exists, the page asks for a different display name or a suffix.
- Supported category scope is only the verified **Sức Khoẻ** category (`c2035652732`) with its four child groups. Other categories are rejected; the form does not guess or silently default a category.
- The page saves the product first, selects it, then creates the run. If product save succeeds but run creation fails, the product stays saved and selected, the page says the product was saved, and a retry creates only the run. A successfully saved product is never duplicated by retry.
- After a run is created, the form locks to that run and the create action is replaced by **Tạo lượt khác**. **Tạo lượt khác** opens a new editable draft, clears the old launch binding, and keeps the created run in **Theo dõi lượt**. While the run request is still pending, editing the draft prevents a late create response from being attached to the changed draft; the run remains in history. A successfully saved product stays selected in the new draft and is not saved twice.
- Failures stay visible inline and map `PRODUCT_INPUT_INVALID`, `PRODUCT_CATEGORY_UNSUPPORTED`, `PRESET_ID_EXISTS`, `PRESET_NAME_EXISTS`, `PRESET_BUSY`, and `PRESET_WRITE_FAILED`. A `PRESET_WRITE_FAILED` can also mean the remote Node/tsx builder is unavailable.

The bridge validates the same request shape before sending it. Test the flow with fake bridge responses; do not point a test config at the real presets or runs folder.

## Review sampling

A request-v2 run stores its collection policy when the run is created. After verified M2, the flow binds that policy to one automatic attempt and uses it for the whole run and direct M3. The M3 panel shows the frozen policy read-only; extra collection is available under **Lấy thêm theo cách khác**, which saves an immutable extra plan and launches that exact plan by digest. It never changes `request.json`, the M2 selection, or a stored result. Viewing and saving a plan are offline; source counts, launch, stop and reconcile call the remote CLI.

- Modes: `with-comments`, `all`, and `stars` (`1..5`, sorted unique). The saved policy accepts N from 1 to 2000 per link. A repeated automatic M3 refuses with `AUTOMATIC_COLLECTION_EXISTS`; an explicit extra collection uses the saved-plan and plan-SHA route. Legacy request-v1 runs keep the old cap of 300 and are labelled **Lượt tạo bằng bản cũ · tối đa 300 mỗi link**, never silently rewritten.
- Order is `native-filter-ascending-stars-v1`: selected star filters are traversed sequentially ascending. Pooled spends one shared remaining N low-star-first, so it may finish before a higher selected star. Equal-stars is optional, available only in `stars` mode, and stops each star at its own equal quota without filling from another star.
- Source counts are native rating counts, including ratings without text; they are not the number of eligible written reviews. A missing or unknown count is shown as **chưa có số liệu**, never `0`. An observed `0` on a loaded filter is a verified empty result.
- Outcomes keep requested, written actual and shortfall separate. Zero-result, partial, exhaustion, timeout, cancel and control-changed are distinct. A running checkpoint is `checkpoint`, not a terminal outcome. Only text reviews are collected; there is no media field, count or claim.
- A changed M2 digest invalidates the old plan: the panel drops it and launching it fails with `REVIEW_PLAN_CHANGED` before any worker starts.
- The read-only guard is the remote marker `${SHOPEE_FLOW_STATE}/shopee-flow/READONLY` (or `TDN_SHOPEE_FLOW_READONLY=1`). With `SHOPEE_FLOW_STATE` isolated, the marker blocks counts, launch and reconcile while offline viewing and saving of the review plan remain usable; saving a plan is not a DB import. Exact-attempt stop remains usable. Do not change a shared or production guard for a test.
- Offline coverage: `skills/tdn-shopee-flow/tests/test_sampling.py` runs the real CLI against a synthetic M2-pass run with isolated `SHOPEE_FLOW_RUNS` and `SHOPEE_FLOW_STATE`, Node 24 and the repository `tsx`. Launch without a collector configuration fails closed with `COLLECTOR_NOT_CONFIGURED`; no journal is written and no network is used.

Run status (app 1.2.2): one damaged run never fails the run list; its row shows «Chưa xác định được trạng thái» (`status` `UNKNOWN`, `execution` null, its error code) and stays openable and deletable. A run whose work was stopped (worker ended unfinished, `RUN_INTERRUPTED`, or the user stopped the step-3 attempt) has run status `STOPPED` («Đã dừng») in both the list and the details.

## Save and export collected comments

Every M3 run shows **Kết quả và tải file** after collection, independently of whether the current M2 input is readable. The panel uses stored settled results only; it never reruns Metric, Shopee, or a collector. The operator chooses one exact stored source, then uses **Tải file JSON**, **Tải file TXT**, or **Lưu vào hệ thống**. Opening the panel or refresh does not save, import, or download anything.

- The source selector stays on the exact selected source across refreshes. If that source disappears, the panel requires a new selection instead of silently choosing another one.
- JSON and TXT availability are per format. Under the read-only guard, a new DB save and new JSON/TXT generation are blocked; only an exact export with an existing cache receipt remains downloadable. The panel shows the blocked reason or that receipt.
- Export runs offline through the bridge route `export-review-data`, then streams the exact file through bridge-private `read-review-export`. The desktop asks for a native Save As destination and sends only the sanitized suggested base name to the dialog. Raw contents and filesystem paths do not cross into the page, logs, or error text.
- The bridge accepts at most 64 MiB, verifies the declared size and SHA-256 while streaming, and only replaces the chosen destination after both checks pass. It uses a temporary file in the destination folder, so a failure or cancel leaves the existing destination and no `.part` file. Cancel is a normal result, not an error.
- Save uses `save-review-data` with exactly `{sourceSha256}`. Export uses `export-review-data` with exactly `{sourceSha256, format}`. A changed source, missing proof, or blocked format is shown with its static reason; it is never retried against a different source.

## Step 4 and notifications

Under step 3, **Bước 4 Lưu và phân loại bình luận** shows save, filter and label from `review-process --run` (`review-process-view-v1`). **Chạy tiếp** appears only when the source stopped with `canResume: true`; it sends `process-review-data --run <id> --source-sha256 <sha> --detach` and expects `review-process-start-v1`. The header status line and the run status chips read `runs-progress` (`runs-progress-v1`), one call for all runs about every 15 seconds. The bridge rejects any key or enum value outside these three formats.

A notification fires once per change seen between two polls (run started, step passed, step stopped, run finished), never for the first poll after the app starts. With the window in front it is a notice at the bottom left; otherwise the bridge method `notify(title, body)` shows a Windows toast. The toast runs the system `powershell.exe -NoProfile -NonInteractive -WindowStyle Hidden -EncodedCommand <constant script>` (WinRT `ToastNotificationManager`); title and body travel only in environment variables and become XML text nodes. No package is added to the build, nothing listens in the background, and no network is used. Off Windows `notify` does nothing and answers ok.

Offline coverage: `python3 -m unittest discover -s tools/shopee-desktop/tests -p 'test_step4_bridge.py' -v` and `node --test tests/integration/shopee-desktop-ui.test.ts`. The demo page `index.html?mock=1&s4=<s1run|s3run|running|pass|fail|old>` shows each approved scenario; its first progress poll answers the state just before the scenario event, so the notification appears on the next poll.

Build one windowed executable with the spec in this folder. It bundles `index.html`, the shared `../opencli-metric/clis/metric/request-in-page.js`, `tdn_metric_browser`, `vendor_pychrome` and `websocket-client`:

```powershell
.\.venv\Scripts\python.exe -m PyInstaller --noconfirm --clean TDN-Shopee-Flow.spec
```

The build bakes `VERSION` (and the short git sha when git is there) into the executable as `app-version.json`; the app shows it small in the bottom right corner («v1.0.0»).

**Version rule.** `VERSION` holds `X.Y.Z`. Each PR that changes the app raises it: the minor number for a feature (`1.1.0`), the patch number for a fix (`1.0.1`). At each EXE release the coordinator writes `{"version":"X.Y.Z"}` to `~/.local/state/tdn-shopee-modules/app-latest.json` on the server. The app reads it with `app-latest` (`app-latest-v1`) after it connects and every 30 minutes; a newer version shows «Có bản mới X.Y.Z. Liên hệ để lấy file cài.» Closing it hides that version only (kept in `%APPDATA%\tdn-shopee-flow\app-update-dismissed.json`). The app never downloads or installs anything.

The executable is `dist\TDN-Shopee-Flow.exe`. It reads the same external config and loads the bundled page from PyInstaller's extraction directory. Use the Python `--check` command above for visible console diagnostics, since the windowed executable has no console. Closing the window does not stop a detached remote run.

Windows packaging and GUI rendering must be verified on Windows; the Linux checks cover the import, bridge and CLI only. Live capture/collection remains subject to the owner's separate authorization and the remote guard.

## Windows with WSL

To use the SSH client and authentication already configured inside WSL, replace `sshCommand` with this placeholder-only example:

```json
{ "sshCommand": ["wsl.exe", "--exec", "ssh", "-T", "-o", "BatchMode=yes", "<user>@<host>", "bash", "-s"] }
```

Keep the other config fields as described above. The bridge sends UTF-8 bytes with LF line endings through WSL to the remote shell.
