# I08 · Rào cản

Spec v1.0.0 · coverage `DRAFTED` · authority `PROPOSED_LOCATED_BARRIER_METHOD` · implementation `NEW_CODE_IF_APPROVED` · readiness `NOT_ASSESSED` · execution/review `NOT_RUN`.

## Question and boundary

Which directly documented barrier interrupted a stated task or outcome, in what context, and what source evidence records the next step? A complaint alone does not prove a barrier or its market frequency. No new research collection is proposed.

## Inputs and procedure

Required: existing located source, owner-defined task/outcome scope, `EvidenceRecordRef`, explicit attempted task or goal, barrier wording, context, product/offer version if source gives one and next-step/outcome if recorded. A versioned owner-approved barrier codebook is required for grouping. Stable case/episode ID is optional for a single located case and required for linking separate event records.

1. Freeze eligible records. Check that source describes a specific goal/attempt and an obstacle before coding it as a barrier. If only a general dissatisfaction is given, retain it as a statement, not a task barrier.
2. Record task, obstacle, stage, context, exact quote/event, source-reported version and result. Each field gets a locator or explicit `not stated`. No product/version identity is inferred from names.
3. Apply only approved barrier codes and preserve coder/adjudication. Keep counterexamples and unresolved explanations. Deduplicate repeated exact evidenceRecordRef values or a real stable same-source record key, never text alone; without person identity, count located evidence cases, not unique people.
4. If measuring incidence, require a compatible sampled task denominator and documented sampling frame. Otherwise output only located examples/record counts. Absence from the corpus is not absence of a barrier.

No inferred severity, probability, lost-customer value or fix priority. Missing outcome differs from successful completion and failure. Sort deterministically by source digest and locator.

## Output, example and limits

Output: barrier record and task/context fields, direct source refs, product version only if source-supplied, result state, codebook/adjudication, counterevidence and denominator/coverage status. Toy fixture: one located support record says checkout could not accept a stated payment method and task ended. Expected one documented barrier example, no prevalence or lost-sales estimate.

Blocked fixture: a negative rating exists without text or attempted task. Expected `I08_TASK_BARRIER_NOT_ESTABLISHED`; preserve rating as its original measure, no barrier code.

Allowed: “This source records barrier B during task T.” Cite exact spans. Forbidden: all customers face B, causal churn/lost sales, severity ranking, solution or product-quality claim without separate evidence.

AI role: candidate code only against approved taxonomy and source excerpt; human adjudication required. Required task/context/obstacle fields come directly from the source; I02/I04/M13 are optional reusable outputs. Open choices: barrier taxonomy, coding unit, task-success definition, denominator, severity/priority policy. Proposed blockers: `I08_TASK_CONTEXT_MISSING`, `I08_BARRIER_LOCATOR_MISSING`, `I08_CODEBOOK_UNAPPROVED`, `I08_PREVALENCE_DENOMINATOR_MISSING`. Reopen on source/version/codebook change. Acceptance: negative rating without task remains unclassified; missing result does not become failure; record counts never become people counts without IDs.

Record identity: apply the common-rules record-identity policy. Collapse only repeated exact evidenceRecordRef values or records proven identical by a stable source key. Identical wording at different row/span locators remains distinct; text hashes alone never authorize record deduplication. Corpus counts are coded records, not people.
